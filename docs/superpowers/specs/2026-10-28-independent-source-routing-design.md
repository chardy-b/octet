# WIL-250 — Independent manual input selection with the active output DSP

## Outcome and scope

Rich can choose an available Tidal, AirPlay, or analog USB input without first changing to the **Output DSP controls** preset. The selected input feeds the *same currently approved* eight-output CamillaDSP chain; source selection does not choose a different speaker preset. Implement in Octet's existing Python, CamillaDSP YAML and web UI, not C++. The user approved preserving the active approved output profile on 2026-10-28. This document is the design review gate, not permission to deploy or unmute the Pi.

## Existing behavior and alternatives

`pi/remote/server.py:select_source` currently requires `CHANNEL_PROFILE` and rewrites that preset in place. Its `source_config` helper prepends an input mixer and changes only capture/clock fields, but has no durable recovery contract for a different approved profile. The web UI disables source selection if `source_switching_available` is false. Automatic AirPlay and manual Bluetooth have separate SHA-verified baseline candidate/journal mechanisms; Auto Tune holds an audio-device lease. The live Pi has previously used a 129-filter Auto Tune baseline, while the channel preset has 37 filters. Neither a Git checkout nor a DSP `Running` response proves physical safety.

1. **Selected: derive a checked, temporary capture route from the active approved profile.** Keep the original approved baseline byte-identical. Serialize and journal its identity, use a bounded candidate in `/var/lib/octet-dsp`, switch while muted, verify the loaded config, and recover to the original path on failure or restart. For the classic channel profile, retain the existing managed source behavior unless unification demonstrably improves safety without losing persisted settings. This reuses established AirPlay/Bluetooth safeguards without introducing another audio daemon.
2. **Always load `CHANNEL_PROFILE` when a source changes.** Rejected: this could silently replace the user's active crossover, EQ, output mutes and protections with a different 37-filter chain.
3. **Move source selection into an upstream PipeWire/ALSA mixer so CamillaDSP never reloads.** Deferred: it adds another clock/ownership boundary to a system whose recent WirePlumber enumeration failed under active ALSA owners. It is not a safe shortcut for this ticket.

## Authority, invariants and ownership

- Accept only an active `CHANNEL_PROFILE` or a SHA-verified `TUNING.active(path)` baseline whose loaded CamillaDSP JSON is semantically identical to the approved YAML. Require Auto Tune `audio_owned is False`, DSP `Running`, a recognized stereo Tidal-loopback original capture, and supported device rate/format. Unknown, altered, foreign, unapproved or concurrently changing paths fail closed. Never fall back to the channel preset.
- **Output invariant:** downstream pipeline, all existing speaker filters/mixers, output map, playback device, polarity, per-output mute, EQ, gain, and protection stay exactly equal to the original approved profile. Only a narrowly allowlisted input mixer plus capture/clock fields may differ. Check this structurally against the original before publishing a candidate and against the loaded config after reload. Reject ambiguous existing `octet_source` metadata or an unsupported topology.
- The active automatic AirPlay cast, Bluetooth session/journal, manual route, and Auto Tune device lease are exclusive owners. Use `server.LOCK` for cooperative actions and the existing cross-process `audio.lock` lease for baseline route mutation; a pending journal is an owner, not permission to overwrite. A manual override may first stop/recover a current automatic owner while muted; if recovery fails it must stop there. Automatic receiver start while a manual candidate is active must either recover the manual route first under the same lock or refuse before any automatic unmute; it must never layer candidate-on-candidate. Explicit source selection outranks stale AirPlay/BT callbacks, not a fresh competing owner.
- CamillaDSP's websocket has no atomic compare-and-set. This design does not claim to exclude non-cooperative CamillaGUI or manual websocket clients. Mutations require the existing guarded-control boundary and runtime readback; attended physical acceptance additionally requires isolating other writers, as in the repo audio deployment gates.

## Manual source transition and recovery

1. Discover/validate the requested source ID and hardware availability before changing audio. Detect owner and current route. A request for the already-selected source is a verified no-op, never an implicit unmute. Preserve MPD queue, track and position.
2. With ownership established, command and verify master mute before changing a path; pause MPD without clearing its queue. For approved baselines, preserve original path, exact approved bytes/digest, loaded config, previous source identity and a bounded generation in a durable journal. Generate an ephemeral candidate from the *original* approved profile for each requested source. For a second manual switch, replace the active candidate only through a generation-safe, muted transition; do not derive from a previous temporary route or accumulate input mixers. Keep enough journal evidence to restore the original after any interruption.
3. Candidate publication: validate allowlisted deltas, CamillaDSP `--check`, safe bounded regular-file ownership and permissions, fdatasync and directory fsync, then durably journal before `SetConfigFilePath(candidate)` and `Reload`. Recheck original approval/digest, lease and current path/config immediately before the switch. Avoid `SetConfigJson`, which applies immediately. Confirm `Running`, candidate path, exact expected loaded config, original digest and mute. For USB validate device/rate and selected capture readiness; for manual AirPlay, selection alone means waiting for a cast, not active playback.
4. Success stays **muted**. Tidal requires explicit Play; USB requires explicit Unmute. No source change may silently raise master volume. Do not auto-resume the Tidal queue or auto-unmute AirPlay/Bluetooth as a consequence of *manual* selection. Existing automatic AirPlay/BT activation and their bounded −18 dB checks remain separate behaviors.
5. On failed validation, reload, ownership, readiness or readback: re-mute; restore the original approved path/config and prior safe source when possible; verify loaded bytes/config, path, DSP running and mute before deleting candidate/journal. If recovery cannot be verified, retain journal and mute/retry latch, expose a specific blocked state, and refuse unmute or another source change. At remote startup, recover a stale manual journal while muted before accepting controls; do not auto-play or auto-unmute. If an external owner changed the path, retain evidence and refuse to overwrite it. An ephemeral manual selection does not promise to survive a restart: after safe recovery, the original approved baseline/Tidal route is selected and muted. Existing channel-profile source persistence remains unchanged.

## API and UI contract

- `source_switching_available` means that the active profile and ownership permit a **safe manual change**, not that the path equals `CHANNEL_PROFILE`. Include a concise reason for blocked selection (e.g. Auto Tune owns outputs, unapproved DSP configuration, recovery pending, disconnected input); a foreign/unknown configuration must not show an enabled selector.
- List available sources independently of the active approved output profile. The UI keeps the current source and pending selection stable across status polling, displays selected/waiting vs actual AirPlay cast status, and confirms that manual switching remains muted. The DSP page must show the active output profile accurately while an ephemeral input route is loaded, not mislabel it as an editable channel preset. Existing Auto Tune output editing constraints remain unchanged; this ticket does not make read-only saved baselines editable.

## Tests, deployment and acceptance

- Regression tests: channel-preset round trips; representative approved 129-filter baseline Tidal → USB mono/stereo → AirPlay waiting → Tidal; equality of the entire output subtree and original baseline bytes; candidate check/reload/readback; missing device, invalid metadata/topology, changed approval/digest, stale/crash journal, failure before/after path mutation, failed restore, and no accidental unmute or volume increase.
- Arbitration tests: simultaneous AirPlay start/stop, Bluetooth session/journal and Auto Tune ownership; repeated or stale events cannot steal the route, delete recovery evidence or unmute a foreign candidate. UI tests: enabled on an approved baseline, disabled with specific reason when unsafe, source and DSP labels correct. Keep existing receiver guards intact.
- Exact branch tests and CI plus skeptical independent audio-safety review are required before publishing a code PR. The implementation branch is stacked on the current WIL-249 candidate until AirPlay/Bluetooth branches land; reconcile with their current exact heads before any PR. A safe code/CI result does **not** authorize changing the Pi, enabling Bluetooth, restarting services, or physically unmuting speakers. Live deployment needs a separate approved muted maintenance plan and attended low-level source-to-speaker acceptance with full graph/PCM/route checks and rollback.

## Open design-review points

- Reuse or extract the existing `airplay_baseline.py`/`bluetooth_route.py` durable-route primitives without weakening their distinct automatic receiver state machines; implementation may choose a small shared helper after focused tests. Do not create a third competing journal format whose recovery order is undefined.
- Confirm the active saved profile's exact capture topology and allowed rate/format on the real Pi *read-only* before deployment; a unit fixture is not proof that every approved Auto Tune baseline can be routed.
