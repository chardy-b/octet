# WIL-251 — Unified Tidal, AirPlay and Bluetooth input selection

Status: Rich approved the behavior in chat on 2026-10-28. This is a design for review, **not** authorization to install on the Pi, open pairing, interrupt current playback or unmute speakers. It builds on WIL-248 AirPlay, WIL-249 Bluetooth, and WIL-250 independent source routing; those draft branches and their physical gates remain separate.

## User contract

The Music page offers **Auto, Tidal, AirPlay, Bluetooth** as source choices. A named choice is a manual override and has precedence over automatic input events until the user selects Auto. The UI shows both requested mode and effective route, including waiting for a cast, connected-but-idle Bluetooth, active stream, unavailable receiver and blocked recovery. A manual choice does not depend on which approved output DSP profile is active. All three inputs feed the same approved CamillaDSP output chain and one master fader; no per-source preset, output EQ, crossover, polarity, output mute, playback device or protection changes are allowed. No simultaneous input mixing.

- **Manual Tidal:** select the Tidal capture route muted, preserve queue/position; only deliberate Play resumes the queue. Pause/stop does not release manual precedence.
- **Manual AirPlay:** select/wait muted for a cast. A fresh cast or freshly verified currently active cast is a separate playback intent and may unmute through the guarded AirPlay path; selecting AirPlay alone never does. A stopped cast leaves AirPlay selected but muted/waiting. A pre-existing cast must pass live receiver/PCM/generation checks; do not replay a cached callback or treat the selection itself as proof of streaming.
- **Manual Bluetooth:** select/wait muted for a previously paired/authorized connected phone; do not initiate media playback on the phone. A connected-but-idle phone makes the requested Bluetooth source visible as waiting, not audible. Only a fresh or freshly verified active A2DP stream may start the guarded BlueALSA bridge and unmute. If multiple connected devices compete, the first fresh authorized active stream wins; do not select a device by untrusted display name or a browser-supplied MAC. A stopped stream leaves Bluetooth selected and muted/waiting. Pairing/discoverability remains a separate, explicitly authorized toggle; source selection never opens it.
- **Auto:** when no input is playing and no manual override exists, an already-paired phone's new connection may set Bluetooth as the *requested/waiting* source, but cannot load an audible route or unmute. A validated active A2DP stream can take that idle route. A fresh AirPlay cast can take an idle route. Active playback remains owned by its current input; competing automatic sources do not steal it. On stop, mute and release the owner, restore the approved idle route, then consider a **freshly validated** other active stream; never auto-resume Tidal. A deliberate Tidal Play changes to manual Tidal to protect that choice from later automatic events. A later named selection takes over an automatic route through the full muted recovery path.

Manual selection stays in effect across pause/stop. On upgrade, initialize intent to **Auto** to preserve existing automatic AirPlay behavior, but keep Bluetooth automatic admission disabled until its separate reviewed deployment and physical acceptance gates pass. Persist **intent** (Auto or named source) separately from physical DSP routing; on restart, recover any journaled route to the approved baseline, boot muted, and display the saved intent as waiting. Do not replay an old receiver event, resume MPD or unmute from persisted intent. A new cast/stream requires fresh admission after startup gates. If an established intent file is corrupt or unreadable, fail muted and display an explicit unknown-intent/blocking state rather than silently changing priority.

## Alternatives and chosen architecture

**Chosen: one small source coordinator over the existing guarded receivers and WIL-250 manual route.** It owns requested mode, effective owner, generation and transition decisions under the existing controller lock. Keep AirPlay's hook, Bluetooth's stream observer/bridge, Auto Tune's lease, and their distinct PCM endpoints. The coordinator asks each route to prepare/stop/recover under the existing cross-process audio lease and checks *all* other recovery journals before mutation. Receiver events carry their generation to avoid stale takeovers. Do not fork another DSP output profile or add a second audio output daemon.

**Rejected: direct UI calls to each source controller.** They leave competing priority/intent rules in separate handlers and cannot make a manual Bluetooth choice or a shared status contract reliable. **Deferred: upstream PipeWire/ALSA input mixer.** It introduces another clock/device owner and a new graph failure mode after the recent WirePlumber ownership incident. This feature needs one exclusive input, not mixing.

A manual override may stop and fully recover the automatic owner before preparing its selected source; if stop, bridge reap, mute, journal restore or lock verification fails, retain evidence and refuse the new route. Automatic events cannot preempt a manual choice. An unsupported, altered or foreign active DSP configuration cannot be converted by falling back to `CHANNEL_PROFILE`. Rebuild candidates only from the exact SHA-approved original baseline; WIL-250 output-equivalence validation must hold before and after DSP reload. Preserve MPD queue, track and position and the existing dedicated Loopback sub0/sub1/sub2 assignments. Auto Tune's audio ownership blocks all switches. Keep the existing guarded-control/privileged Bluetooth socket boundaries; a web choice is a narrow source intent, not arbitrary root access, device pairing or MAC trust.

## Common volume and audible-start rule

Use CamillaDSP's single master level as the shared level; switching inputs does not reset it to −18 dB or maintain separate per-source values. The default UI ceiling remains **−18 dB** for every source. The existing explicit **Unlock higher levels** action may permit a *later deliberate manual volume adjustment* on any selected source, up to the existing manual limit; it is not inherited as permission for an automatic start. The receiver watchdogs must distinguish that deliberate, current manual authorization from an automatically admitted stream rather than treating a manual UI selection as an automatic high-volume exception.

Before **any** automatic audible start (Auto mode or fresh cast/phone stream while manually selected), mute, read back master volume and cap a louder value at −18 dB; leave an already quieter value unchanged. Verify the new level, approved DSP config/path/output chain, exclusive owner, current event generation, receiver service, both matching PCM endpoints and advancing capture/playback pointers, then unmute with post-readback and watchdog. A direct source choice alone stays muted. An explicit unlock/raise after playback starts is a new deliberate action requiring guarded revalidation; it must never allow a stale generation, disconnected receiver or a later automatic restart to inherit the higher level. Expose the cap in status if it lowered a previously unlocked level. −18 dB is a digital master ceiling, **not** a calibrated acoustic SPL or proof of safe playback for arbitrary media.

## Failure, UI and acceptance

On route mismatch, stalled PCM, disconnect, service loss, unsafe level, Auto Tune takeover, unexpected writer, journal collision or failed recovery: mute first, stop/reap the receiver bridge where applicable, restore the exact approved baseline only when owned and safe, retain a retryable journal/latch otherwise, and block unmute and further switching. The status response must report requested mode, effective source, receiver/stream state, owner and actionable blocked reason without exposing phone identifiers unnecessarily. The web UI must not claim Bluetooth is playing merely because it is connected; nor claim a recovered Tidal baseline is the saved manual input. Browser source actions need existing host/origin controls, narrow validated IDs and no arbitrary device address or shell command.

Test-first matrix: manual Tidal/AirPlay/Bluetooth/Auto round trips and persistence; auto BT connection without PCM (waiting and muted), fresh stream starts, idle connection does not start a phone app; AirPlay and Bluetooth events during manual choice and active other input; two phones and stale/replayed generations; shared fader and manual-unlock versus automatic-start cap; unchanged whole output subtree on a representative approved baseline; queue retention; failures before/after mute, bridge reap, route reload and journal recovery; startup with pending journals; UI labels, disabled reasons and explicit waiting/active status. Run exact-head CI and independent skeptical audio-safety review. Reconcile against moving WIL-249/WIL-250 heads before implementation or delivery.

**Physical release gate:** code/CI alone does not authorize deployment or unattended unmute. First complete parent AirPlay/Bluetooth review and effective socket/runtime-directory repair, exclusive DSP-writer boundary, supported Pi graph/PCM and rollback checks. Then obtain a separately approved muted maintenance window and perform attended low-level Tidal, AirPlay and paired-phone trials, including manual overrides, idle Bluetooth connection, fresh stream, volume readback, crash/stop, reboot and physical speaker output. Keep the work draft and the Pi unchanged until that gate is met.

## Open implementation questions for the plan

- Choose the minimum shared intent/state representation and its atomic, least-privileged persistence path; avoid a fourth competing DSP recovery journal. Test corrupted/missing intent fail-closed.
- Reconcile parent WIL-249 observer's current fresh-stream-only admission and root-only manual Bluetooth control with the new read-only connected/waiting state and narrow web choice. Validate the real Pi connection/stream ordering before enabling auto starts.
- Refactor receiver-specific −18 dB startup/watchdog logic only after tests distinguish automatic activation from deliberate in-session manual high-volume control. Do not weaken the current automatic ceiling to make the UI unlock work.
