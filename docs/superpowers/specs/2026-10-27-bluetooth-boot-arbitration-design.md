# Octet: boot-ready open Bluetooth and source arbitration

Status: approved direction, implementation pending. This extends WIL-249 and depends on WIL-248. **The later [automatic-stream/pairing-toggle amendment](2026-10-27-bluetooth-auto-stream-pairing-toggle-design.md) replaces this document's always-discoverable pairing behavior:** pairing is off by default and enabled only by an explicit, persistent, authorized web toggle; existing paired phones still play when it is off. The remaining stream-admission, priority, DSP isolation, boot, and rollback gates here still apply. Neither document permits unattended speaker playback on the Pi before those gates pass.

## Outcome and deliberate exposure

After a reboot, Octet may advertise its Bluetooth A2DP sink, but **new pairing is closed unless the user enabled it through the reviewed web toggle**. While pairing is on, any nearby device can pair without approval and later send music; a stranger in radio range can connect, churn, or interrupt idle playback. Turning pairing off stops new bonds, not previously paired devices. There is no promised radio-range denial-of-service defense while pairing is on. Do not describe open pairing as access-controlled. Avoid offering headset, microphone, file-transfer, or network services. Missing or invalid root policy fails closed; old allowlist-only policy remains a rollback mode. The installer must default to pairing off.

Only while the authorized web toggle is effectively on in open mode, a dedicated BlueZ `Agent1` advertises `NoInputNoOutput` and accepts Just Works pairing without confirmation. Register a single default agent only while the root-owned open policy, BlueZ adapter and A2DP-sink-only BlueALSA service are healthy. Set/read back `PairableTimeout=0` and `DiscoverableTimeout=0` (intentional indefinite window), then enable/read back `Pairable=true` and `Discoverable=true`; remove the agent and close both properties when the toggle is off, the policy is invalid, or the receiver stops. Reject `AuthorizeService` for UUIDs other than A2DP/AVRCP audio-source control, and refuse PIN/passkey methods rather than fabricating credentials. Verify by read-back and by attempting a non-audio service with a test device; BlueZ may still expose its own built-in profiles, so block unattended open pairing if a non-audio profile is actually usable. Existing paired devices must also pass current paired/connected/transport checks; no trust inference from a displayed name.

**Boot readiness is not boot playback:** start the receiver after BlueZ and the protected Octet controller are ready; register the pairing agent only if the persistent web pairing toggle is on and its checks pass. Boot CamillaDSP muted and MPD stopped. Never start a speaker route solely because a device is paired or connected. A newly active, validated A2DP stream may request guarded routing. Keep the receiver optional: a Bluetooth daemon failure must not shut down Tidal, AirPlay, or the web controller.

## Priority and ownership

Priority is **AirPlay > explicit web-UI Tidal/source choice > automatic Bluetooth > idle Tidal**. This is an ownership policy, not mixing. Each transition takes the controller's shared lock, mutes before changing the DSP route, and is journaled/recoverable; the previous protected speaker processing stays semantically identical except for the selected capture endpoint.

- The first Bluetooth device with an active, validated stream owns the Bluetooth slot. A second Bluetooth stream cannot displace it; after the first stream stops or disconnects, a fresh stream from another device may acquire it.
- An AirPlay start may preempt Bluetooth: mute, terminate and reap the owned BlueALSA bridge, restore/verify the approved baseline and release its cross-process audio lease, then prepare AirPlay. If any step fails, remain muted and reject AirPlay rather than running both. AirPlay's ordinary 10-second capture readiness and -18 dB startup rule still apply.
- When AirPlay ends, restore the source selection it interrupted. If that was Bluetooth and the same device still has a *fresh* active stream, it must pass the full guarded start again; otherwise stay muted on the approved Tidal baseline. If it interrupted a deliberate Tidal selection, restore Tidal selection and queue without automatically resuming music.
- A web-UI Tidal selection or playback action overrides Bluetooth and remains selected after Tidal pause/stop. A new Bluetooth connection does not steal that explicit selection. A deliberate later web action may relinquish it. The existing manual actions must never bypass recovery or silently resume MPD.
- An AirPlay stop/start replacement and a Bluetooth stream handoff must not resurrect an earlier owner from a stale hook, D-Bus event, or journal. Serialize transitions and bind callbacks to a generation/owner identity; fail muted on ambiguity.

## Bluetooth admission and audio safety

A persistent agent may accept only the intended Bluetooth pairing method while the authorized web toggle is on and the open policy is valid. Register it only after the receiver and policy are valid; remove it on toggle-off, shutdown, or rollback. A paired device is not automatically a valid audio source: read BlueZ's current device and transport identity, paired/connected state, A2DP source role, BlueZ/BlueALSA bus owners, and the active stream/codec. Use a *specific observed address* for the bridge, never an all-zero wildcard or a user-supplied unverified string. Do not treat a transient connection as an active stream. Block concurrent or unauthorized device handoffs. Rate-limit pairing and activity logs without storing audio, phone identifiers beyond what BlueZ needs, or secrets in logs.

The automatic admission machine observes `idle → active` for one BlueZ `MediaTransport1` A2DP source. A generation is the current BlueZ unique bus owner + BlueALSA unique bus owner + exact Device1 and transport object paths + a local monotonically increasing transition counter. A fresh active transport at controller startup may form a generation only after all boot gates pass and two consistent identity reads; a mere `Connected=true` never does. Pin the first accepted generation and its specific bridge child until transport idle, disconnect, service-owner change or a higher-priority takeover. Ignore stale callbacks from older generations. On transport idle for at least one second, clear the generation; on disconnect, clear it immediately. An error latches that generation: no retry while the same active stream continues. A new active edge after a full idle/disconnect, or an explicit administrator retry, can try again. Bound observations to the current verified D-Bus owner; never replay a cached event after controller restart.

Re-use WIL-249's dedicated `hw:Loopback,0,2` → `hw:Loopback,1,2` path. Keep MPD on sub0 and AirPlay on sub1. No direct DAC, PipeWire Bluetooth profile, or default-device fallback. Require the same approved Auto Tune baseline, unmodified output filters/tweeter protection, mute-first checked candidate, exact playback/capture format and owner, advancing hardware/application pointers, service/identity continuity, and watchdog. Automatic Bluetooth must never exceed the existing **-18 dB DSP master ceiling**; a quieter current level remains quieter. This is a digital bound, **not** an acoustically calibrated safe SPL or proof that arbitrary full-scale media cannot damage speakers. On idle, failed PCM, disconnect, service loss, timeout, changed owner, or recovery failure, mute first, stop/reap the bridge, and restore the prior route or keep a recovery latch; no retry loop on the same stream. Only a new stream generation after a clean stop may retry. Automatic playback has no arbitrary wall-clock cutoff while healthy music continues (AirPlay-like): a lease expires within one second unless the 0.25-second watchdog renews it after rechecking generation, policy, DSP ownership/config/mute/volume, both PCM owners/formats and four advancing pointers. Missing one renewal or two seconds without PCM progress mutes and ends the session; never extend a lease from connection state alone. The existing 30-minute limit remains for explicit manual admin sessions, not the new automatic mode.

The CamillaDSP websocket is a non-cooperative write surface. Stopping CamillaGUI for one attended session is not an unattended exclusion mechanism. Before boot-time automatic unmute is permitted, run CamillaDSP with systemd `PrivateNetwork=yes`, still binding its *private* loopback at `127.0.0.1:1234`. A companion proxy with a *distinct* service UID (`octet-dsp-proxy`, not `octet`) and `JoinsNamespaceOf=camilladsp.service` enters that network namespace, forwards complete WebSocket connections to the private TCP listener, and exposes only `/run/octet-dsp/control.sock` in the shared filesystem. Its runtime directory is owned by `octet-dsp-proxy:octet-dsp-control` mode `0750`; its socket is mode `0660`. Add only controller UID `upmpdcli` and a *distinct* Auto Tune service UID to that group; the proxy additionally checks `SO_PEERCRED` on each connection against those exact identities. The current Auto Tune service runs as `octet` and must be migrated to its own service identity with reviewed file/audio permissions. Change `pi/remote/server.py`'s `DSP.__enter__` and `measure/octetmeasure/autotune/camilla.py` plus deployed clients to dial the Unix socket instead of direct TCP. CamillaGUI and arbitrary `octet`-UID scripts must not be able to dial either the socket or the private listener. This is a design gate, not a claim that the installed CamillaDSP binary already supports Unix sockets. Refuse automatic unmute if namespace, proxy, peer credentials, or either authorized client is unavailable; integration-test access allowed/denied on the actual Pi and verify that host `127.0.0.1:1234` is unreachable. Disable CamillaGUI at boot as a reversible part of this change. Root with systemd/network-namespace control remains trusted; arbitrary local root is outside the threat model. Preserve Tidal/AirPlay and Auto Tune behavior during migration; rollback must restore their previous direct-TCP clients together with the old CamillaDSP unit, never leave a half-migrated audio path. Do not rely on a pre-unmute read-back plus watchdog alone to justify open, unattended output.

## Service composition and boot health

The current WIL-249 `bluetooth.conf` overrides WIL-248's `RuntimeDirectoryMode=0750` with `0700` for *both* runtime directories. This denies Shairport access to `/run/octet-airplay/control.sock`, even though the socket is group-writable. The attended AirPlay cast initially failed for this reason and succeeded after a **temporary** group-traversal permission change. Fix the effective systemd runtime-directory composition in the reviewed repository and test both Shairport's real group access and the root-only Bluetooth control socket after restart/reboot. Do not widen Bluetooth control privileges merely to repair AirPlay.

Enable the A2DP sink at boot through a reviewed optional unit with explicit dependency/ordering on BlueZ and controller readiness; do not enable Debian's packaged `bluealsa`/`bluealsa-aplay` units. Preserve package masks and the isolated `monitor.bluez` exclusion. **Controller ready** means the web control socket is responding, CamillaDSP is Running/muted on the SHA-verified approved Auto Tune baseline, no AirPlay/Bluetooth recovery journal or Auto Tune audio lease is outstanding, the exclusive DSP proxy is verified, and CamillaGUI is disabled/inactive. A boot graph gate waits at most 30 seconds for the `octet` user's WirePlumber and these five exact nodes from `docs/agent-workflows/audio-deployment.md:10-12`: `alsa_card.platform-snd_aloop.0`, `alsa_output.platform-snd_aloop.0.analog-stereo`, `alsa_input.platform-snd_aloop.0.analog-stereo`, `alsa_card.platform-soc_107c000000_sound`, and `alsa_output.platform-soc_107c000000_sound.stereo-fallback`. It also checks ALSA card identities and sub0/sub1/sub2 owners, MPD stopped, and the DAC hardware pointer advancing on two samples a second apart. A running DSP alone is not enough. Previous boot produced only HDMI/`auto_null` nodes until owner-free WirePlumber recovery, and the DAC once stalled with DMA errors. If any boot gate fails, leave the receiver connectable only if it cannot reach the speakers, refuse automatic route/unmute, keep DSP muted, and report a diagnostic; do not restart WirePlumber while PCM owners are active. Fix boot ordering or use separately reviewed muted owner-free recovery and verify after an actual reboot. Keep AirPlay discovery, playback and stop/restore healthy with Bluetooth receiver active.

## Implementation and acceptance gates

1. Preserve a backup and exact hashes of the deployed code, systemd files, policy, graph, baseline and MPD queue before mutation. Provide a single reviewed reversible installer and rollback path. All config writes explicit and atomic where compatible with the policy contract; read back effective service state, not only file contents.
2. Write focused test-first coverage for open-policy validation/agent lifetime, bounded events and generation changes, first-stream-wins, AirPlay preemption and restoration, persistent Tidal override, all failure/latch paths, no cross-source PCM collision, and systemd override composition/socket access. Existing restricted/manual mode must still work and fail closed.
3. Run exact-head CI, independent safety review, and real Pi preflight before an attended, conservative-volume phone trial. Demonstrate the web toggle's off/on effective state, public pairing with a **second** previously unpaired device only while on, and that device's reconnect/playback while off. A test with only the existing Pixel does not establish open pairing or off-state behavior.
4. Verify two competing Bluetooth devices, AirPlay interrupt and handback, Tidal override through pause/stop, disconnected source, daemon/controller crash and restart, long-running session, and mute/recovery. Inspect live capture/output meters, both sub2 pointers, DAC pointer, unchanged crossover/output protections, and actual speaker sound at low level. Never claim silent or mocked tests are physical acceptance.
5. Perform an attended **reboot** and read back BlueZ, discoverability/agent, optional sink, GUI/exclusive DSP boundary, full Loopback/DAC graph, baseline/mute, MPD queue, and fresh phone/AirPlay playback. If any gate fails, boot must remain muted and rollback must restore the previous manual receiver and AirPlay behavior.
6. WIL-248 PR #1 is the parent of WIL-249 PR #2. Do not merge the child to main before its parent and this change are reviewed and verified. PRs remain draft until exact-head checks, physical gates, and rollback are recorded; user permission to merge does not waive a failed safety gate. Update Linear WIL-248/WIL-249 with actual results and blockers.

## Non-goals

No Bluetooth microphone/call path, file transfer, network PAN, direct DAC route, simultaneous mixing, remote Internet exposure, or claim that -18 dB is a calibrated acoustic limit. No automatic Tidal resume after AirPlay. No permanent change to the speaker EQ/crossover to make source switching easier.
