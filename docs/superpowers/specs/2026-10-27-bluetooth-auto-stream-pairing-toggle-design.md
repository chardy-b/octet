# WIL-249: automatic Bluetooth playback and web pairing toggle

Status: approved direction, source foundations only; **automatic playback and the pairing toggle are not implemented or deployed**. Rich approved a simpler source implementation after the renewable-lease candidate failed review: use the existing bridge/PCM and controller/DSP watchdogs instead of a new cross-thread heartbeat lease. This amends [the boot/source-arbitration design](2026-10-27-bluetooth-boot-arbitration-design.md). Its safety and rollback gates remain in force. The earlier design's always-discoverable behavior is replaced by the pairing toggle below; automatic playback still requires an actual A2DP stream. It does not change the separate WIL-248 parent PR dependency.

## Outcome and observed baseline

A phone already paired with Octet can connect and press Play without a terminal or manual `bluetooth_admin.py start`. Octet routes that phone's audio through the current guarded BlueALSA → dedicated Loopback sub2 → approved CamillaDSP speaker chain and stops it safely on disconnect or failure. Connecting or pairing without starting music does **not** cause Octet to play a track on the phone, claim the DSP route, or unmute. The user controls whether **new** nearby phones can pair using a visible web toggle; turning it off does not revoke existing pairs or block their playback.

In an attended Pixel 11 Pro trial, the manual bridge became active, both sub2 endpoints were RUNNING with advancing pointers, DSP was Running at −18 dB, and Rich heard audio. The phone was paired/trusted. This establishes the live manual path, **not** automatic admission, reconnect, boot readiness, or a calibrated speaker limit. Octet is currently manually operated; do not treat this specification as permission to change the live Pi without a reviewed install and attended test.

## Admission and priority

- Boot muted with MPD stopped and no Bluetooth bridge. Start the optional A2DP sink/observers only after controller, DSP, graph, and policy readiness. A paired/connected `Device1` is not playback intent.
- Observe a *fresh* BlueZ `MediaTransport1` A2DP source transition into active streaming. Validate its unique BlueZ/BlueALSA bus owners, exact device and transport object paths, paired+connected identity, authorized admission policy, codec, and two consistent reads. Pin an owner/generation; ignore stale/replayed callbacks, and do not admit a second device until the first releases its slot. On a valid active stream, invoke the same guarded route as manual start using the observed MAC, not an ambient/default device.
- The automatic path mutes first, keeps the MPD queue/position, checks the approved baseline and candidate, and only unmutes with advancing/owned playback and capture pointers and DSP volume ≤ −18 dB. This is a digital ceiling, **not** a calibrated acoustic SPL or protection against arbitrary source material. The existing bridge supervisor checks PCM progress, child and bus owners on each observation, while the controller's existing watchdog checks the active transport generation, DSP state/level and route ownership. A failure mutes and reaps through the same manual recovery path. Automatic sessions have no arbitrary elapsed-time cutoff; manual sessions retain their 30-minute lifetime. Do not add a separate heartbeat-lease mechanism.
- Preserve the prior approved priority: AirPlay > explicit web-selected Tidal/physical source > automatic Bluetooth > idle Tidal. A web-selected source stays selected across pause/stop; a fresh Bluetooth stream does not steal it. After AirPlay ends, re-admit a fresh still-active Bluetooth stream only through the full gate; never auto-resume Tidal. Stop, disconnect, stale generation, drift, timeout, daemon/controller loss, or failed recovery mutes and restores/retains a recoverable journal. No automatic retry on the same failed stream generation.
- The existing manual admin start/stop and restricted allowlist mode remain available as a rollback and diagnostic path.

## Pairing toggle and access boundary

- The web UI has a clearly labeled **Allow new Bluetooth pairing** toggle with observed state and a warning: **while on, any nearby phone may pair and subsequently play audio; this is not access-controlled**. The default on fresh install is off. The explicit choice persists through reboot until changed. Off closes discoverability/pairability and withdraws the temporary pairing agent; it does not delete BlueZ bonds, revoke trust, stop an existing session, or block an already paired phone from connecting and playing. The toggle must report verified *effective* adapter/agent state rather than merely the requested value. If the effective state cannot be confirmed, show an error and fail closed to new pairing.
- Keep root ownership of the durable policy and pairing control. The Tailscale-only web service must not receive arbitrary root access or a generic BlueZ command proxy. Use a narrow local privileged service/socket with `SO_PEERCRED` checks for `upmpdcli` and exact `enable`/`disable`/`status` operations. For a web mutation, pass the observed peer Tailscale IP to that service; it must resolve the live Tailscale WhoIs user identity and compare its stable user ID with an explicit root-owned administrator allowlist (default empty until provisioned). Reject unknown, tagged, subnet-routed, or changed identity and never trust an HTTP forwarding header. Also enforce the web endpoint's existing host/origin checks and same-origin JSON mutation contract. Octet's Pi has `tailscale whois --json`; its actual user-ID mapping and socket access still require a real preflight. If identity cannot be verified, disable the web toggle rather than granting every Tailnet visitor permission. No toggle operation edits the MAC allowlist or invokes arbitrary shell.
- In open mode only, register the reviewed `NoInputNoOutput` agent and allow bounded A2DP/AVRCP service authorization. Refuse unrelated services; verify on real BlueZ that built-in non-audio profiles are not usable through this pairing flow. If that cannot be demonstrated, do not enable open pairing. Close/withdraw the agent on toggle-off, controller failure, invalid policy, or receiver loss. A device paired during an open window remains paired after the window closes; the UI should say so.
- A restricted mode can continue to require explicit allowlisting/trust; the pairing toggle is not a backdoor around that policy. The installer is disabled-by-default and must not silently open pairing on upgrade or rollback.

## Unattended output safety and service gates

- Prior to unattended unmute, eliminate the documented non-cooperative CamillaDSP websocket writer race. Adopt the reviewed private DSP listener plus peer-credential-checked Unix proxy design in the parent spec, including scoped Auto Tune identity and atomic migration/rollback of *all* clients; `camillagui inactive` at one instant is not sufficient. Verify the host cannot dial the private DSP listener and unauthorized UIDs cannot dial the proxy, while Tidal/AirPlay/Auto Tune still work.
- Repair the effective systemd `RuntimeDirectoryMode` composition so AirPlay's `shairport-sync` still reaches its group-controlled socket and Bluetooth remains root-controlled. Preserve WirePlumber's BlueZ isolation and the five named Loopback/DAC graph nodes. Do not restart WirePlumber while MPD/Camilla own ALSA endpoints. Fail closed at boot if protected baseline, graph/PCM owners, DSP proxy, optional sink, or journal recovery is not ready.
- A reviewed installer backs up bytes/modes/unit states, deploys a narrow exact-hash manifest, boots muted, and can roll back to the verified manual receiver and existing AirPlay/Tidal behavior. Code, policy, pairing agent, receiver registration, auto-routing, and physical speaker acceptance are separate gates. No live reboot, service restart, pairing exposure, or unattended output is authorized by this document alone.

## Verification and delivery

1. Test-first coverage for off/on/persistent toggle, authorization and CSRF/host/origin rejection, effective-state readback, agent lifecycle and non-audio profile refusal; both restricted and open policy modes.
2. Event/generation tests for paired idle connection (no route), active stream admission, stop/disconnect/reconnect, two competing phones, stale bus owner, failed route/latch, and boot with an already active transport. Check MPD queue retention, AirPlay and explicit web-source priority, ≤ −18 dB, failed-DSP fail-closed behavior, and no regression in manual start.
3. Exact-head CI and independent safety review; Pi-only proof of DSP proxy privilege separation, AirPlay socket access, full graph, sub2 PCM owners/formats/pointer progress, DAC output, and rollback. Test a previously unpaired second phone while pairing is on, then prove it can reconnect and play while pairing is off; a third new phone must be denied while off. Use an attended low-volume listening check and a real reboot. Record actual results against WIL-249 and keep PR #2 draft until its parent and physical gates pass.
4. The UI must not describe a Bluetooth DSP candidate as a generic "Other DSP preset" or imply Tidal playback while Bluetooth owns output; expose connection, stream/route, pairing-effective state, and actionable failure without leaking phone identifiers in routine logs.

Non-goals: triggering playback inside the phone when its music app is paused; Bluetooth calls/microphone, file transfer or PAN; simultaneous audio mixing; direct DAC/default-PCM fallback; public internet administration; a claim that -18 dB is an acoustically safe maximum.
