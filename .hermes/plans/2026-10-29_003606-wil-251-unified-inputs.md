# WIL-251 Unified Input Selection Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task. This approved-design handoff is for implementation, not deployment.

**Goal:** Octet lets Rich choose Auto, Tidal, AirPlay or Bluetooth at any time; manual choice wins, Auto recognizes an idle paired Bluetooth connection and plays only validated streams, with one speaker DSP and shared level.

**Architecture:** Add a narrow source-intent coordinator over the current manual source route, AirPlay hook and Bluetooth stream observer/controller. Persist requested intent separately from physical DSP recovery journals; route handoffs remain exclusive, mute-first and fail-closed. Reconcile against the moving WIL-249/WIL-250 parent branches before publishing.

**Tech Stack:** Python 3 stdlib/unittest, existing PyYAML/CamillaDSP websocket, ALSA Loopback, BlueZ/BlueALSA D-Bus, vanilla JS/Node browser smokes; no new audio daemon or per-source output preset.

## Global constraints and system map
- **Compatibility:** Pi 5 / existing `pi/remote` service and approved Auto Tune baseline; preserve `CHANNEL_PROFILE` behavior, Tidal queue/position and dedicated sub0/sub1/sub2 routes. WIL-248, -249 and -250 PRs are draft, and WIL-249 is concurrently moving. Preserve existing dirty work in other worktrees.
- **Dependencies:** reuse `airplay_control.py`, `bluetooth_auto.py`, `bluetooth_control.py`, `manual_source_route.py` and their guarded DSP journals. No direct DAC, PipeWire audio mixer, shell command from web, generic root socket command, or unknown DSP preset fallback.
- **Security and operations:** server `LOCK`, `audio.lock`, mutually exclusive recovery journals, approved baseline digest/output invariant, receiver generation/PCM and service watchdogs. `OCTET_BLUETOOTH_AUTO` remains opt-in until full physical gate. No Pi writes/restarts, discoverability changes, unmute or unattended activation under this code task.
- **Product contract:** `Auto`, `Tidal`, `AirPlay`, `Bluetooth`; manual intent persists and blocks automatic takeover. Auto idle paired connection means Bluetooth waiting/muted; *active verified stream* may unmute. First validated automatic admission committed under `LOCK` owns the idle route; connection-only waiting is not ownership. Shared DSP master level/−18 dB default cap; explicit unlock after active manual control is owner/generation-bound and clears on handoff/restart, while any automatic audible start clamps only if louder than −18 dB. No Tidal auto-resume or phone-app remote play.
- **Verification:** `python3 -m unittest` focused tests in `pi/remote`, Node/browser smokes and exact-head CI if published. Skeptical independent audio-safety review. Real Pi acceptance remains a separate consent gate.

## Risk checks
- The current Bluetooth `_idle()` refuses any manual source journal and automatic start while MPD is paused; a route handoff must adjust both without weakening lease/journal exclusion.
- Current AirPlay `tick()` resets the level to −18 dB; preserve quieter values and prevent a web volume action from being mistaken for settings-only versus playback takeover.
- Current `server._action` stops Bluetooth on every action, including volume/mute/other settings: classify actions by actual output side effect so a benign volume update does not end music, while start/retry/recall remain guarded.
- A connected device does not imply PCM. The phone app cannot be commanded to play by this feature.
- A successfully tested source branch is not a Pi deployment. Physical output, current graph, effective unit/socket permissions, private DSP writer exclusion, rollback and attended speaker observation remain open gates.
